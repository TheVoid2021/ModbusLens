## 2. 第一条：逐句解析

### 2.1 "用纯 C++20 实现 Modbus RTU 分析核心"

- **精确含义**：协议解析、事务分析、统计、诊断规则全部在 `src/core/`，编译成一个静态库 `modbuslens_core`，只用 C++ 标准库。这一点是实测过的：性能基准程序用一个不带 Qt 的 g++ 直接链接这个库就能编译运行。
- **被问怎么答**："核心是一个纯 C++20 静态库，编译时不需要 Qt。它跟界面、串口、网络之间没有依赖，所以三种数据源都能复用同一套判断逻辑。"

### 2.2 "与 Qt/UI 解耦"

- **精确含义**：Qt 只出现在三处——串口适配器、ModelScope 网络客户端、界面桥接与 QML。Core 里没有 QObject、没有信号槽。
- **被问怎么答**："Qt 只是外设和界面的适配层。CRC、帧、事务、统计、诊断这些判断都在纯 C++ 里，可以脱离 Qt 单独编译和测试。"
- **追问准备**："为什么强调解耦？" → "因为三种数据源都要复用同一套判断，界面也不该参与协议事实的判定。"

### 2.3 "覆盖 CRC16、RTU 帧编解码"

- **精确含义**：CRC-16/MODBUS 是自己按位实现的，没有引库，初值 0xFFFF、多项式 0xA001 反射形式、**低字节先上线**。帧模型存地址、功能码、数据，**刻意不存 CRC**，因为 CRC 是线路层的东西，归编解码器管。编解码的错误模型用 `variant` 表达"成功或具体错误"，不是异常也不是错误码返回值。
- **被问怎么答**："CRC 是按位实现的，没引库，位序是线上低字节在前。帧模型故意不存 CRC，因为那是线路层职责。解码结果用的是 variant，成功和失败都是返回值的一部分，调用方必须显式处理失败分支。"
- **追问准备**："为什么不用查表？" → "v1 的场景是 10 帧/秒，按位法远小于 1 毫秒，没有性能需求也没有 profiling 证据就不优化，查表优化记在待办里。"
- **追问准备**："为什么不用异常报错？" → "Modbus 解析失败是正常业务情况，不是异常事件；用 variant 强制调用方处理每一条错误路径，也避免异常影响时序。"

### 2.4 "和 FC03、FC06、FC16 功能码"

- **精确含义**：FC03 读保持寄存器，主动（串口读取）和被动（日志回放）都支持；FC06 写单寄存器、FC16（0x10）写多寄存器**只有被动解析**——能读懂历史流量里的这两类事务，包括回显不匹配这种语义问题，但工具本身不发起任何写操作。
- **被问怎么答**："读的 FC03 主动被动都支持；写的 FC06 和 FC16 只做被动分析，日志里出现这两类事务能判读出回显是否匹配，但工具不发起写操作。全仓库没有任何写路径的代码，这个是可以用 grep 检查的。"
- **追问准备**："为什么不做主动写？" → "诊断工具的定位是旁路观察。一旦具备写能力，工具就从观察者变成参与者，风险完全不同，所以架构上就把写路径排除了，不是暂时没做。"
- **追问准备**："FC03 数量上限为什么是 125？" → "RTU 帧最大 256 字节：响应帧是 5 字节头加上 2N 字节数据，2N ≤ 251，所以 N ≤ 125。"

### 2.5 "把事务结局和协议违规事实拆成 7 类状态与 14 类 Issue"

- **精确含义**：7 是 `TransactionStatus` 的枚举成员个数：Pending、Success、Exception、CrcError、Timeout、ProtocolError、ExpectedNoResponse，回答"这笔事务最终是什么结果"。14 是**两个正交枚举相加**：响应侧 10 个（地址失配、数量失配、正常帧畸形、异常帧畸形、帧过短、意外功能码、FC06 回显失配、FC16 回显失配、广播收到响应、防御性 Unknown），请求侧 4 个（数量越界、长度非法、声明的 byteCount 不符、非法广播功能），回答"判定时具体看到了什么违规事实"。Issue 的结构是枚举码加稀疏载荷，expected/actual 这些字段只在需要时填，对外有稳定的机器 token。
- **被问怎么答**："状态回答'这笔事务是什么结果'，Issue 回答'判定时看到了什么具体事实'，两者互不覆盖。7 个是状态的枚举成员数；14 个 Issue 是两组正交枚举相加，响应侧 10 个、请求侧 4 个。"
- **追问准备**："为什么不把 14 个 Issue 直接做成状态？" → "统计、界面、Agent 白名单都消费状态那条轴，从 6 个状态扩到 20 个会连锁破坏所有穷举分支和既有数据；Issue 是旁挂的一维，老数据集的行为逐位不变。"
- **追问准备**："什么叫稀疏载荷？" → "每个 Issue 只填自己需要的那几个字段。地址失配填 expectedAddress/actualAddress，数量失配填两个数量，其他字段留空，不为了结构统一而塞一堆无意义的值。"

### 2.6 "可以准确表达'响应成功但请求参数违规'这类复合结果"

- **精确含义**：具体形态是 `Success + InvalidRequestByteCount + InvalidRequestLength`——从站正常响应、事务判成功，但捕获到的请求本身声明的字节数与数量对不上、长度也不符。旧模型只有一个粗粒度的 ProtocolError，这些细节在归一化时会全部丢失。
- **被问怎么答**："比如日志里一笔请求声明的 byteCount 和数量对不上，但从站正常回了响应。这时事务结局是成功，请求违规是另一维事实，两个都报出来。旧模型只有 ProtocolError 一个粗分类，细节会丢。"
- **追问准备**："请求侧的 Issue 谁产生？" → "只有被动分析器产生。主动模式下请求是自己构造的，默认可信，这条契约没被推翻。"

## 3. 第二条：逐句解析

### 3.1 "将日志回放从整批失败重构为逐记录诊断"

- **精确含义**：旧实现把"自己构造的请求一定可信"这个主动模式契约套在了历史流量上，日志里一出现 FC06、FC16、通用异常响应、非法请求或广播，整批分析直接失败——一条坏记录毁掉整个文件。重构后只有文本语法错误仍然是整文件失败，其余都变成单条记录的事实：能分析的进统计，不支持的进 `unsupportedRecords` 显式列出。
- **被问怎么答**："原来一条坏记录会让整批分析失败。我把两类失败分开了：文本格式坏了才整文件失败；帧能解析成功之后，不管是语义违规还是不支持的函数，都按单条记录报出来。统计只统计能分析的部分，不支持的那些显式计数，界面上给一条非致命提示。"
- **追问准备**："这样会不会静默丢记录？" → "不会。能分析的进统计桶，不支持的进另一个桶并在界面披露，两个桶的行数加起来等于文件里的有效记录数。"

### 3.2 "Simulator、Serial、Replay 共用同一套分析与统计核心"

- **精确含义**：三种数据源只负责产生字节流——模拟器造字节、串口收发字节、回放读日志。拿到字节之后都进同一个核心做帧解码、事务判断和统计，串口事务会话里直接调用核心的分析函数，没有第二套实现。
- **被问怎么答**："三种模式的区别只有数据从哪来。拿到字节之后是同一个核心做解码、判断和统计，所以同一批数据在三种模式下结论一致。这也是核心不依赖 Qt 的原因。"
- **追问准备**："怎么保证没有偷偷复制逻辑？" → "核心是独立静态库，串口和回放都链接它；功能改动只改核心，三种模式一起生效。"

### 3.3 "为广播事务引入 ExpectedNoResponse 状态，成功率统计排除广播"

- **精确含义**：地址 0 是广播，协议规定所有从站执行但都不回应。判成功等于假称写入成功，判超时等于把合法行为当故障，所以新增第七个状态。统计上 completed 包含广播，但成功率的分母是 `completed − expectedNoResponse`，分母为 0 时返回 nullopt 而不是 0%。
- **被问怎么答**："广播本来就不该有响应。判成功是假称写入成功，判超时是把正确行为当故障，所以单独建了一个状态。成功率分母把广播排除，否则一段合法广播会把成功率稀释得很难看；全批都是广播时分母为零，返回'无法计算'而不是 0%。"
- **追问准备**："广播的写到底成功没有？" → "通信层无法证明。工具只报'观察到广播请求且没有观察到响应'，这既不证明成功也不证明失败，要确认得靠后续回读。"
- **追问准备**："广播收到响应怎么办？" → "那是真异常，从站不该回应。状态判 ProtocolError，同时记一条 UnexpectedResponseForBroadcast，通常意味着有从站把自己的地址配成了 0，或者网关回声。"
- **详细版**：见 11 §5「广播与广播语义」。

### 3.4 "在确定性事实层上接入大模型和 3 个只读 Agent 工具，协议事实由核心判定，模型只做解释"

- **精确含义**：下发给模型的是核心已经算好的结构化事实，一次请求最多 20 条事务明细，不是原始字节流。三个只读工具是会话摘要、最近异常、事务详情，白名单在类型层封闭——不存在写操作的枚举值、分支或工具 schema。运行时还有 3 轮对话、6 次工具调用的硬上限，以及"捕获快照 vs 当前批次"的双层过期守卫。
- **被问怎么答**："模型拿到的是核心已经判定好的结构化事实，不是原始报文，所以它没有机会重新判 CRC 或者超时。三个工具都是只读，白名单在类型层就封闭了，没有写操作的枚举值和分支可派发。再加上轮次和调用次数的硬上限、结果过期就作废的守卫。"
- **追问准备**："模型胡说怎么办？" → "它只能在散文层面胡说，事实层的数字不会变。另外 prompt 里有证据边界约束，只允许对当前观察批次下结论，不许外推成长期结论——这个是踩过一次坑之后加的。"
- **追问准备**："工具调用协议是真是假？" → "做过真实链路的验证，模型返回的是原生 tool_calls，参数回填后能正确产出最终答案。"

## 4. 第三条：逐句解析

### 4.1 "24 个 CTest 目标全绿"

- **精确含义**：24 是注册到 CTest 的**测试目标数**，一个目标对应一个测试可执行文件、一个 .cpp。底下是约 325 个用例、约 1900 条断言。按能力分层：CRC、帧、编解码、FC03、模拟器、故障注入、事务、统计、回放解析、回放分析、被动分析、串口会话、串口适配、界面桥、诊断、AI、Agent 等。核心的测试不依赖 Qt，也不依赖硬件。
- **被问怎么答**："24 是测试套件数，不是用例数，里面大约 325 个用例、1900 条断言，按能力分层切的，哪一层坏了立刻能定位。核心的测试不依赖 Qt 和硬件，跑得很快。"
- **口径细节**（被追问数字对不上时用）：Qt Test 运行时会额外算 initTestCase 和 cleanupTestCase 两条，所以某个目标文件里 53 个用例，运行时报告的是 55 个通过。
- **详细版**：见 §5.1。

### 4.2 "全程 RED→GREEN 留痕"

- **精确含义**：每个阶段先写测试、跑一遍看它失败（RED），再写实现、跑到通过（GREEN），失败数量记进任务档案。有效 RED 的标准是**断言级失败**，不是链接错误——早期确实出现过 undefined reference 那种 RED，后期要求先搭好模型壳，让 RED 真正红在断言上。留痕的例子：某阶段 9 条断言失败、T015 的 13 条断言失败、Part C 的 42 通过 / 12 失败、语义审计那次 21 通过 / 1 失败。
- **被问怎么答**："每个阶段先让测试红一次再实现。RED 有要求：链接错误不算，那是代码没写完；要红在断言上，才说明这条约束真的不满足。失败数量也都记档，13 条断言失败就是'旧链路会把历史流量整批搞挂'的量化证据，重构有没有做完用同一批断言判。"
- **详细版**：见 §5.2。

### 4.3 "用官方协议金样对拍"

- **精确含义**：金样是已确认正确的外部参照数据，对拍是拿实现跟它逐字节比。项目用了三类外部锚点：官方规范里的示例报文（FC03 的请求/响应例子）、真实抓到的报文样本、CRC 独立复算。
- **被问怎么答**："自己跟自己比会一致地错——比如编码和解码的字节序同时反了，互逆测试全绿。所以我拿规范里的示例报文和真实抓到的帧当参照做对拍。我自己踩过一次，把规范上印的线上字节序当成数值记，断言当场把我抓出来。"
- **追问准备**（这个案例讲得越具体越加分）：CRC 那个坑是把 `41 12`、`76 87` 这种**线上字节序**误当成 0x4112、0x7687 这种**数值**记录，只有对着规范原文才能发现。
- **详细版**：见 §5.3。

### 4.4 "为回放链路建立可复现基准"

- **精确含义**：重点不是"我跑得快"，而是"我做了一套可复现的测量方法"：确定性混合样本生成器（八类路径、比例固定、内置与真实帧一致的 CRC 断言）、分段计时的基准程序、多轮取中位数，脚本与原始输出都在仓库。
- **被问怎么答**："我做了一个确定性样本生成器和基准程序，把链路分成读盘、解析、分析三段分别计时，多轮取中位数。样本是八类混合记录，包含成功、异常、CRC 错、超时、FC06、FC16 和两种广播，比例固定可复现，脚本和原始数据都在仓库里。"

### 4.5 "10 万条约 70 ms，解析占三分之二"

- **精确含义**：约 70 毫秒是 10 万条记录的整批耗时，本机 Release 单线程、多轮取中位。"解析占三分之二"是**耗时分布**：在解析加分析这两段里，文本解析占约 65%（两次复跑分别是 65.5% 和 65.7%；100 万条是 62.8% 和 66.1%）。解析做的事是把 `01 03 00 00` 这种十六进制文本逐字符转成字节、并且给每条记录分配容器。
- **被问怎么答**："这不是速度，是耗时分布。链路分读盘、解析、分析三段，解析占大约三分之二，分析三分之一。说明下一刀该切在解析上：容器预留容量、用定长缓冲替代每条一个 vector、十六进制转换改查表。v1 的需求只有 10 帧/秒，所以还没优化。"
- **追问准备**："含不含读盘？" → "不含。按解析加分析两段算约三分之二；把读盘也算上，解析约占六成。"
- **详细版**：见 §5.4。

### 4.6 "100 万条约 0.7 s，从 1 万到 100 万条耗时近似成比例"

- **精确含义**：100 万条约 686.7 毫秒；数据量扩大 10 倍，耗时约 9.7 倍，单条成本近似恒定。
- **被问怎么答**："数据量 10 倍、耗时 9.7 倍，单条成本基本不变。这句话的意义不是快，是验证没有随规模恶化的隐藏问题，比如二次复杂度的配对，或者容器反复扩容。"
- **追问准备**："为什么 100 万条的耗时比按 10 万条速率外推的略快？" → "大份量摊薄了固定开销，文件读取和容器预分配那部分占比变小了。"

## 5. 四个术语的完整解析

### 5.1 CTest

**是什么**：CTest 是 CMake 自带的测试运行器。在 `CMakeLists.txt` 里用 `add_test(NAME 名字 COMMAND 可执行文件)` 把测试注册进去，然后一条 `ctest` 把全部跑完，用退出码判定，可以按名字过滤单个目标，失败时打印输出。

**要和断言框架分开讲**：CTest 负责编排与判定，断言框架负责写用例。这个项目用的是 Qt Test，因为 Qt 本来就是依赖，不想再为一个测试框架多引一个库。Core 保持零 Qt，只有测试目标链接 `Qt6::Test`。

**项目里的事实**：24 个 CTest 目标、24 个测试 cpp、约 325 个用例、约 1900 条断言。

**为什么用 CTest 而不是自己写脚本或点 IDE 按钮**：一条命令跑全部、退出码人和机器都能消费、别人 clone 之后能跑出同样结果；以后接 CI 只改一行，验证入口不变。

**诚实边界**：目前没有接 CI，验证链是本机的 configure / build / ctest / QML smoke / deploy。

### 5.2 RED→GREEN

**是什么**：TDD 的循环。先写测试、跑一遍看它失败（RED），再写实现、跑到通过（GREEN），然后重构。

**要讲的两个实点**：

第一，RED 必须失败在预期的地方。编译不过、链接报 undefined reference，那是代码没写完，不算有效 RED——它只证明功能还不存在。有效 RED 是断言级失败，说明这条约束当前真的不满足。这个要求在项目里是逐步提高的：早期 T004、T005 的 RED 就是链接错误，后期要求先搭好模型壳，让 RED 变成断言失败。

第二，RED 的失败数量是证据。13 条断言在旧链路上真实失败，客观量化了"一条坏记录毒死整批"的代价；重构有没有解决，用同一批断言判。项目里连 RED 的历史都做过订正——承认某次 RED 虽然真实，但没有覆盖每个单元行为。

**被问怎么答**："测试如果从来没红过，你不知道它到底测没测到东西。先让它红一次，证明这条断言真能发现问题。而且失败数量把旧问题的代价量化了，重构做没做完有客观标准。"

### 5.3 官方协议金样对拍

**两个词**：金样就是已确认正确的外部参照数据；对拍就是拿实现跟它逐字节、逐字段比较。

**为什么必须有外部参照**：自己跟自己比测不出系统性错误。编码和解码的字节序如果同时反了，互逆测试会全绿；CRC 自算自验也一样，只会"一致地错"。

**项目用的三类外部锚点**：官方规范里的示例报文（FC03 的请求/响应例子）、真实抓到的报文样本、CRC 用另一套方法独立复算。

**真实踩坑案例**（面试重点素材）：CRC 那个案例里，规范上印的**线上字节序** `41 12`、`76 87` 被误当成**数值** 0x4112、0x7687 记下来，断言当场抓住。这种错误只有拿规范原文当参照才暴露得出来。

**第二种用法——回归护栏**：重构时要求真实样本的四个结局和统计逐位不变，这样"重构"才有可证的等价性，而不是靠感觉说应该没影响。

### 5.4 "解析占三分之二"

**链路三段**：读盘（把 `.mlog` 读进内存，约占一成）、解析（`parseReplayLog`：切字段、解析毫秒数、把十六进制文本每两个字符转成一个字节、给每条记录分配字节容器）、分析（`analyzeReplayLog`：CRC 校验、帧解码、功能码分发、跨帧一致性检查、归类到 7 个状态、填 Issue、汇总统计）。

**实测数字**（去掉读盘，只看解析和分析）：

| 规模 | 解析 | 分析 | 解析占比 |
| --- | --- | --- | --- |
| 10 万条 | 53.8 ms | 28.3 ms | 65.5% |
| 100 万条 | 450.5 ms | 266.5 ms | 62.8% |

第二次复跑：10 万条 47.9 / 25.0 ms（65.7%），100 万条 488.7 / 250.4 ms（66.1%）。

**为什么这句话比"每秒多少条"有含量**：它是一个比例，在任何机器上基本成立，反映的是这段代码的工作性质——文本格式天生要逐字符扫描和分配内存。同时它直接指出了优化方向。

**优化方向**（被问"下一步怎么做"时答）：给记录容器预留容量、请求响应字节改用定长缓冲而不是每条一个 vector、十六进制转换用查表替代逐字符判断，或者干脆出一个二进制日志格式。

**为什么不现在优化**：v1 的场景是 10 帧/秒的实时诊断，用不着；没有真实需求和 profiling 证据就不优化。但分段计时已经做了，瓶颈是已知的。

## 6. 追问题库（Q → 答）

### 协议与建模

| # | 问题 | 答法要点 |
| --- | --- | --- |
| 1 | CRC 为什么自己写不用库 | 学习价值 + 不引依赖；按位实现，用官方金样和独立复算验证正确性 |
| 2 | 低字节在前是什么意思 | Modbus RTU 规定 CRC 低字节先上线；内部存成数值、序列化时拆成低、高两个字节 |
| 3 | 异常响应怎么识别 | 响应功能码等于请求功能码按位或 0x80；**并且请求功能码本身不能带 0x80**（这个守卫是语义审计抓出的 bug，见 §7） |
| 4 | 帧模型为什么不存 CRC | CRC 属线路层，编解码器负责；内存模型只表达语义 |
| 5 | FC03 上限为什么 125、FC16 为什么 123 | RTU 帧 256 字节：FC03 响应 5+2N ≤ 256 ⇒ N ≤ 125；FC16 请求 9+2N ≤ 256 ⇒ N ≤ 123 |
| 6 | 还有哪些功能码能广播 | 标准里写类都能广播；本仓库被动支持集只有 0x06 和 0x10，地址 0 配其他功能码判为非法广播功能 |
| 7 | 三模式怎么保证结论一致 | 核心是独立静态库，三种数据源只负责产生字节，判断和统计全在核心 |

### 架构

| # | 问题 | 答法要点 |
| --- | --- | --- |
| 8 | 逐记录化会不会丢记录 | 分两桶：可分析的进统计、不支持的进显式列表 + 界面提示，两桶合计等于有效记录数 |
| 9 | 为什么拆 Issue 而不是拆状态 | 状态轴被统计、界面、Agent 白名单消费，扩状态会连锁破坏；Issue 旁挂，老数据行为逐位不变 |
| 10 | 成功率分母为什么要排除广播 | 不排除会稀释成功率；把广播当成功则是假称写入成功；分母为零返回"无法计算" |
| 11 | 健康判定为什么不看广播 | 广播没有响应，提供不了正面证据；健康需要正面证据，广播永远不能单独支撑一个健康结论 |
| 12 | 主动和被动契约有什么区别 | 主动模式请求是自己构造的，默认可信；历史流量里的坏请求本身就是待诊断的事实 |

## 8. 数字口径核对表

| 数字 | 精确口径 | 说错会怎样 |
| --- | --- | --- |
| 24 | CTest 测试目标（套件）数，不是用例数 | 说成"24 个用例"会显得测试很少 |
| 325 / 1900 | 用例数 / 断言数（约数） | 报成精确值容易被追问 |
| 7 | `TransactionStatus` 枚举成员数，别漏第七个 ExpectedNoResponse | 漏一个等于承认没掌握自己模型 |
| 14 | 10 个响应侧 + 4 个请求侧，两组正交枚举相加 | 说成"一个枚举 14 个值"口径就错了 |
| 3 | 只读 Agent 工具数；配套 3 轮、6 次调用、20 条明细 | 混着说会自相矛盾 |
| 70 ms / 0.7 s | 整批耗时，Release 单线程，多轮中位 | 说成"平均"要能补"其实取的是中位" |
| 0.709 μs | 是微秒不是毫秒；和每秒条数互为倒数 | 单位说错量级差一千倍 |

| 性能数字性质 | 主机相对值，波动 ±10~15%，非跨机 SLA | 说成生产指标会被要求举证 |
