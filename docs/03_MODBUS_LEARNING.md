# 03 — Modbus 学习笔记（Knowledge Base）

> 状态：持续积累。本文件是团队（含 AI 代理）共用的 Modbus 知识底座；实现协议核心（T002–T004）前必须通读。
> 来源：modbus.org 官方规范（Modbus Application Protocol V1.1b3、Modbus over Serial Line V1.02），以及测试对拍资料（pymodbus、libmodbus 的测试向量）。

## 1. Modbus 是什么

主从（Master/Slave，新称 Client/Server）架构的应用层协议，1979 年由 Modicon 发布，用于工业设备（PLC、电表、变频器、传感器）之间的数据交换。特点是简单、开放、实现成本低，至今仍是工业现场最普及的协议之一。

三种物理承载：
- **Modbus RTU**（串口，二进制紧凑帧 + CRC16）
- **Modbus ASCII**（串口，十六进制字符帧 + LRC，较少用）
- **Modbus TCP**（以太网，MBAP 头 + PDU，无 CRC，依靠 TCP 校验）

本项目的诊断对象以 **RTU 为主 + TCP 兼容解析**。

## 2. 数据模型（4 种数据区）

| 数据区 | 访问 | 大小 | 常见用途 |
| --- | --- | --- | --- |
| 线圈 Coils | 读/写 | 1 bit | 开关量输出 |
| 离散输入 Discrete Inputs | 只读 | 1 bit | 开关量输入 |
| 保持寄存器 Holding Registers | 读/写 | 16 bit | 参数、设定值 |
| 输入寄存器 Input Registers | 只读 | 16 bit | 模拟量采样 |

> 坑：协议 PDU 内地址从 0 计数（0x0000 = 第一项）；而"40001 保持寄存器"这类编号是 1 计数的人读地址（40001 → 寄存器 0）。诊断工具必须明确区分并展示两种口径，这是常见 off-by-one 错误源头。

## 3. RTU 帧结构（ADU）

```text
┌──────────┬──────────┬───────────────┬──────────┐
│ 从站地址  │ 功能码    │ 数据（N 字节）  │ CRC16(低)│ CRC16(高) │
│ 1 B      │ 1 B      │ 0–252 B       │ 2 B      │
└──────────┴──────────┴───────────────┴──────────┘
      帧内 t1.5 静默    帧间 t3.5 静默（帧切分依据）
```

- 地址 0 = 广播；广播只允许写类功能码，无响应。
- 帧间必须 ≥ 3.5 字符时间的静默，否则接收方可能把两帧粘在一起。
- 例（9600-8E1，每字符 11 bit）：1 字符 ≈ 1.146 ms，t3.5 ≈ 4.01 ms，t1.5 ≈ 1.72 ms。
- 超过 1.5 字符时间的帧内静默视为帧中止（部分设备容忍度不同,诊断时值得记录）。

## 4. PDU 与功能码

| 码 | 名称 | 说明 |
| --- | --- | --- |
| 0x01 | Read Coils | 读线圈 1–2000 |
| 0x02 | Read Discrete Inputs | 读离散输入 1–2000 |
| 0x03 | Read Holding Registers | 读保持寄存器 1–125 |
| 0x04 | Read Input Registers | 读输入寄存器 1–125 |
| 0x05 | Write Single Coil | 单线圈 | 0xFF00=ON, 0x0000=OFF |
| 0x06 | Write Single Register | 单寄存器 |
| 0x0F | Write Multiple Coils | 多线圈 |
| 0x10 | Write Multiple Registers | 多寄存器 1–123 |
| 0x16 | Mask Write Register | AND/OR 掩码写 |
| 0x17 | Read/Write Multiple Registers | 先写后读 |
| 0x2B | Encapsulated Interface Transport | 厂商扩展 |

异常响应：功能码 | 0x80 + 异常码：

| 异常码 | 含义 |
| --- | --- |
| 0x01 | 非法功能码 |
| 0x02 | 非法数据地址 |
| 0x03 | 非法数据值 |
| 0x04 | 从站设备故障 |
| 0x05 | 确认（处理中） |
| 0x06 | 从站忙 |
| 0x08 | 存储奇偶校验错误 |

| 0x0B | 网关目标设备无响应 |

## 4.5 T015 官方协议事实回填（2026-09-13，人工 Review 后入档）

> 来源：**MODBUS Application Protocol Specification V1.1b3** + **MODBUS Serial Line Protocol and Implementation Guide V1.02**。只记录本阶段（T015 Phase B）需要的确定事实；不接受新证据的一律不入档（不猜常量）。

- **FC06（0x06 Write Single Register）**：
  - Request：register address（uint16）+ register value（uint16）。
  - Normal response：**echoes request**（字段与值完全回显）——exact-echo 是事务判定的依据（不匹配 ⇒ 独立 issue `WriteSingleRegisterEchoMismatch`，不是 MalformedNormalResponse）。
  - Exception function：**0x86**。
- **Function 0x10（Write Multiple Registers）——仅知识回填，本 Phase 不实现 normal semantics**：
  - quantity = **1..123**；byteCount = **2×N**（N=写入寄存器数）。
  - Normal response = **starting address + written quantity**（不回显数据）。
  - Request PDU 字段顺序：starting address（2B）+ quantity of registers（2B）+ byte count（1B）+ register values（2N B）；**实际 value 字节数必须与 byteCount 一致**。
  - Exception function = **0x90**（经 generic exception matcher 识别）。
  - T015 Part C 立项（2026-09-14）：**仅被动 normal semantics** 纳入实现范围（Active Serial 仍 FC03 read-only）。
- **Generic Exception**：exception function = request function + **0x80**；exception payload = **一个 exception code**（单字节）。
- **Broadcast**：serial address = **0**；**no response returned**；broadcast requests are **writing commands**（写类功能码）——**不**扩大解读为“所有 address=0 的功能码都合法”。

## 5. CRC-16/MODBUS

- 参数：Poly 0x8005（反射多项式 0xA001），Init 0xFFFF，RefIn/RefOut = true，XorOut 0x0000。
- 校验值（ASCII "123456789"）= **0x4B37** —— T002 必测的规范向量。
- 经典示例请求帧：`01 03 00 00 00 01`（从站 1，读 1 个保持寄存器，地址 0）→ CRC = **84 0A**（低字节在前）。其 CRC 部分（84 0A）归 **T002** 向量验证；完整帧的编解码金样归 **T003**（对拍 pymodbus/libmodbus 双确认）。
- 实现选择：按位法（教学清晰）vs 查表法（性能，用 0xA001 反射形式最简洁）。**T002 仅实现按位法并验证正确性**；查表法优化与性能基准不在 T002 范围，留待后续单独拆分的优化任务（见 BACKLOG T013 备注）。
- CRC 保证"检错"，不"纠错"；理想条件下漏检率约 2^-16（依多项式性质）。
- 面向理解与面试的完整解读（10 个必答点、两个权威测试向量、未来伪代码逐步解读）→ **§10**。

## 6. Modbus TCP（MBAP）

```text
┌─────────────┬─────────────┬──────────┬──────────┬─────────────┐
│ 事务标识     │ 协议标识     │ 长度       │ 单元标识   │ PDU         │
│ 2 B         │ 2 B (=0)    │ 2 B       │ 1 B       │ n B         │
└─────────────┴─────────────┴──────────┴──────────┴─────────────┘
```

- 端口 502；长度字段 = 单元标识(1) + PDU 字节数。
- 事务标识用于请求-响应配对；本项目事务分析的配对逻辑直接借鉴此思想（RTU 无此字段，靠时序+地址+功能码启发式配对）。

## 7. 字节序与数据解释（诊断高发坑）

- 16 bit 寄存器在帧内为**大端**。
- 32 bit（float/int32）跨两个寄存器时，字序（高低字先后）设备间不一致 = 现场数据"看不懂"的头号原因 → 诊断平台必须支持可配置的字节序/字序解释，并能在报告中提示可疑模式。

## 8. 典型通信故障（诊断规则的素材池）

| 现象 | 常见根因 |
| --- | --- |
| 无响应/超时 | 地址错、波特率/校验不一致、线序、终端电阻 |
| CRC 错误集中 | 干扰、接地、波特率偏差、半双工冲突 |
| 高异常码频率 | 地址越界（0x02）、值越界（0x03） |
| 间歇性掉帧 | t3.5 不满足、驱动缓冲、线缆 |
| 数据忽对忽错 | 字序/字节序、符号解释、量程换算 |

## 10. CRC-16/MODBUS 深度解读（T002 Phase A 学习成果）

> 本节目标：在写任何 CRC 代码之前，能面向面试官把 CRC-16/MODBUS 讲清楚。口径以初学者能理解为准，不展开有限域数学。
> 协议依据：**MODBUS over Serial Line Specification and Implementation Guide V1.02**（§2.5.6 Error Checking / CRC）。

### 10.1 CRC 在 Modbus RTU 里解决什么问题

RS-485 现场链路长、有电磁干扰、地电位差、波特率偏差，字节翻转、丢失、多收在物理层不可避免。CRC 要解决的问题是：**接收方如何廉价而可靠地判断"这帧和我以为发送的那帧是否一致"**。机制是发送方把"地址+功能码+数据"算出一个 2 字节校验码附在帧尾；接收方对收到的内容重新计算并比较，不同就整帧丢弃——防止把损坏的字节当作命令执行或当作数据上报。

类比：快递单上的"件数+重量"核对栏。目的不是防"有人调包"，而是防"运输过程破损"。

### 10.2 为什么 CRC 不是加密，也不是身份认证

- **没有密钥**：算法是公开规范，任何人都能对任意内容重算 CRC。
- 因此它挡不住恶意篡改：攻击者改完数据、重算一遍 CRC 再发，接收方照样通过。
- **身份认证**要回答"这真是对方发来的吗"，需要密钥/签名/MAC；CRC 回答的只是"这串字节中途有没有意外损坏"。

项目口径：ModbusLens 永不把"CRC 通过"当作安全证据；CRC 失败也不会让我们"看清"正确内容，它只告诉我们"内容不可信"。

### 10.3 哪些字节参与 CRC 计算

RTU 帧里从**从站地址**开始，到**数据区最后一个字节**为止的全部字节——即整帧去掉最后两个 CRC 字节的部分（地址 + 功能码 + 数据）。

**不参与**：帧尾两个 CRC 字节本身、帧前后的 t3.5/t1.5 静默时间、UART 层的起始位/停止位/校验位。

### 10.4 初始值为什么记录为 0xFFFF

两层含义：

1. **它是算法家族定义的一部分**：CRC-16/MODBUS 属于 IBM 系（ANSI/X25 血统），规范就规定初值 0xFFFF。它和多项式一样，是"协议双方约定好的算法参数"，不是推导出来的。
2. **功能意义**：如果初值是 0x0000，那么全 0 的数据、以及消息开头的一串 0 字节，都不会改变寄存器——"没收到数据"和"收到了全 0 数据"在 CRC 上无法区分。用 0xFFFF 作初值后，任何输入（哪怕一个 0x00 字节）都会改变寄存器状态，等于多一层"消息确实开始了"的保护。

### 10.5 每个输入字节如何参与计算

- 一个字节进入时，先被 **XOR 进当前 CRC 寄存器**——这一步对应长除法里"把被除数的下一位(组)带下来，拼进当前余数"。
- 然后循环 8 次（一个字节 8 bit），**每个 bit 依次决定"减不减除数"**：这 8 次按位操作把该字节的每一个比特都混合进余数，并通过后续字节的运算继续扩散到整个 16-bit 结果。
- 所以"每个字节参与计算"= 一次并入 + 8 次按位除法迭代；不是简单相加，字节之间是乘上/除让位过来的，前后顺序敏感。

### 10.6 为什么算法要检查最低位（LSB）

这个算法是"反射（LSB-first）"形式。把 CRC 看成长除法：标准写法最高位在左、商位从左往右产生、每步判断"最左边那一位"。**反射形式把整个运算镜像过来**：寄存器右移、商位从右往左产生，于是"当前要判断的那一位"落在了二进制的最低位置——也就是 LSB。

一句话：**看 LSB 不是拍脑袋，它是"当前这一步商位是 0 还是 1"在镜像坐标系里的位置**。

### 10.7 0xA001 在实现中扮演什么角色

0xA001 是**反射之后的多项式**。

- Modbus CRC 的规范多项式是 **0x8005**（x¹⁶ + x¹⁵ + x² + 1）。
- 位运算里的"减去除数"在模 2 算术中等价于 XOR。
- 本算法用右移、判 LSB（见 10.6/10.8），整个运算方向被镜像，所以每步 XOR 进去的除数也必须是 0x8005 的**位反转：0xA001**。

记忆法：同一个除数，正着写是 0x8005，镜像写是 0xA001。选哪个看算法是"左移判 MSB"还是"右移判 LSB"。

### 10.8 为什么算法使用右移

右移是反射形式的一部分，和判 LSB、用 0xA001 三者必须配套：

| 配套方案 A（正序） | 配套方案 B（反射，本项目采用） |
| --- | --- |
| 左移寄存器 | 右移寄存器 |
| 判断 MSB（0x8000 位） | 判断 LSB（0x0001 位） |
| XOR 0x8005 | XOR 0xA001 |

两套方案数学等价、产出完全相同的线上字节。选 B 的理由是工程直觉好：**串口数据本就是一位一位、按 LSB-first 到达的，反射式按位实现与数据流方向一致**，代码最直白、最适合面试讲解与逐位验证。

### 10.9 计算值 vs 线上两个字节的区别

这是面试最容易踩的点，必须分开记：

- **计算值**：算完寄存器剩的是一个 uint16_t 数，比如 `0x0A84`（十进制 2692）——一个"数值"。
- **线上字节**：这个数要拆成两个字节放进帧尾。Modbus 规定**低字节在前**：0x0A84 的低字节是 0x84、高字节是 0x0A，所以线上一前一后是 `84 0A`。

容易踩的坑：很多"查表工具"显示的是数值，很多"抓包工具"显示的是线上字节序，两者看起来"倒了个"。并不是算错了，是**数值与字节序约定**的差别。

### 10.10 为什么 Modbus RTU 发 CRC 时低字节在前、高字节在后

- **协议依据**：V1.02 规范明确 CRC 以 **least significant byte first** 透传。这是 Modbus 的硬性互通约定，与实现它的 CPU 是大端还是小端无关。
- **历史动机**：CRC-16/IBM 家族的传统（源自 Bisync 时代）；当年的接收设备是逐字节移位寄存器，先收到低字节就可以边收边算、不需要缓存字节重排。
- **工程教训**：实现者绝不能把 uint16_t 直接 `memcpy` 进帧里（那依赖主机端序），必须手工"先写低字节、再写高字节"。

### 10.11 两个权威测试向量（Phase B 的 KAT 基础）

> 记法约定（沿用 10.9）：**CRC 数值** = 寄存器最终 uint16 值；**线上字节** = 帧尾两个字节的实际先后顺序（低字节在前）。

| 向量 | 输入（参与计算的字节） | Expected CRC 数值 | Wire CRC bytes（线上字节序） |
| --- | --- | --- | --- |
| **Vector A** | ASCII `123456789`（31 32 33 34 35 36 37 38 39） | `0x4B37` | `37 4B` |
| **Vector B** | `01 03 00 00 00 01`（从站 1，功能码 03 读 1 个保持寄存器，地址 0） | `0x0A84` | `84 0A` |

- Vector A 是 CRC 世界的通用基准串，用来确认算法实现本身正确；
- Vector B 是完整 Modbus 请求帧，用来确认"参与计算的字节范围"理解正确（只算前 6 字节，不含 CRC 自身）。
- 两个向量已于 T002 Phase A 用独立的一次性脚本复核通过（脚本不进仓库，防污染）。

### 10.12 未来实现的伪代码与逐步解读

```text
crc = 0xFFFF                      (1)

for each byte:                    (2)
    crc = crc XOR byte            (3)
    repeat 8 times:               (4)
        inspect LSB               (5)
        shift crc right           (6)
        if previous LSB was 1:    (7)
            crc = crc XOR 0xA001  (8)
```

每步"为什么存在"：

1. **crc = 0xFFFF**：家族规定的初值，见 10.4——不是凑的数，是 CRC-16/MODBUS 算法参数之一。
2. **for each byte**：CRC 覆盖"地址+功能码+数据"的所有字节（10.3），每个字节都要喂进去。
3. **先 XOR byte**：把一个新字节并入当前余数，等价长除法的"带下一位"（10.5）。顺序敏感，所以字节先后不能换。
4. **repeat 8 times**：一个字节 8 bit，每位要做一次"看商位→移位→视情况减除数"的除法迭代；8 次走完，这个字节才被完全吸收。
5. **inspect LSB**：反射算法里 LSB 就是"当前商位"的镜像位置（10.6）；先看后移，保证判断用的是"被移出去之前"的那一位。
6. **shift right**：把刚处理完的 bit 推出寄存器、把下一位挪到判定位，让 16 位余数逐位与消息呼应；与判 LSB、用 0xA001 配套（10.8）。
7. **if previous LSB was 1**：长除法规则——商位为 1 才需要在这一列减去除数；商位为 0 就只是平移。所以"看的那一位是 1"是执行减法的唯一触发条件。
8. **XOR 0xA001**：模 2 世界里"减去除数"就是 XOR；0xA001 是反射后的 Modbus 多项式（10.7）。减完整 16 位（多项式隐含的最高位 0x10000 不落地，因为右移把它自然带走）。
