# 00 — 项目章程（Project Charter）

> 状态：正式（v1.0，2026-09-05 由 T001 建立）
> 维护：方向性变化时更新；具体技术决策走 ADR，需求变化走 01_REQUIREMENTS + Issue。

## 1. 背景与问题

- 工业现场（电表、变频器、传感器、PLC 从站等）大量使用 Modbus RTU/TCP，排障通常依赖商业调试工具，费用高、无离线分析能力。
- 学习与面试场景中，学生难以接触真实工业设备，需要一个**无硬件即可演示**完整通信诊断过程的工程。
- 秋招项目的核心竞争力之一是可验证的真实开发过程：本工程把"怎么做的、为什么这么做、踩了什么坑"全部固化为仓库文档。

## 2. 愿景

构建一个 **C++20 + Qt6 的 Modbus 通信智能诊断平台**，它同时是一个：

1. 可用的诊断工具（面向模拟/回放/串口三种数据源）；
2. 结构清晰的软件工程教学案例（面向面试官与学习者）；
3. 可随时移交给任何 AI Coding 平台继续开发的工程（面向未来协作者）。

## 3. 目标（Goals）

- G1 三种数据源模式（Simulator / Replay / Serial）使用**同一套**协议解析、事务分析、统计、诊断核心。
- G2 开发全过程可追溯：每个任务在 `docs/tasks/` 留下完整档案。
- G3 平台可移植：项目状态只存储于 Git 仓库内 Markdown，不依赖任何聊天上下文或平台私有 Memory。
- G4 核心功能不依赖 LLM：断网/未配置时功能完整。
- G5 任何协作者按 README + ENVIRONMENT 文档可在 30 分钟内完成构建、跑通测试并演示。
- G6 面试可用：每个里程碑有可演示产出与配套面试问答素材。

## 4. 非目标（Non-Goals）

- 不做商业级 SCADA/组态软件的替代品。
- 暂不实现 Modbus 主站写入控制的下发通道（Agent 更严格限制为只读）。
- 不做实时控制（硬实时）承诺，性能目标以满足诊断场景为准。
- 不追求跨所有 Qt 旧版本兼容，最低 Qt 6.5，开发基线 Qt 6.11。

## 5. 核心原则

1. **可构建、可测试、可演示优先于一切。** 任何时刻仓库主线都必须处于可构建状态。
2. **核心逻辑纯粹化。** 协议与诊断核心与 I/O、GUI、LLM 解耦，可独立单元测试。
3. **模式复用，杜绝复制。** 新增模式 = 新增数据源适配器，而非复制核心。
4. **记录即交付。** 未记录的开发过程视为未发生。
5. **只增不改的档案区。** 历史记录永不删除、永不覆盖。
6. **Agent 只读。** LLM Agent 初期只有只读诊断能力。

## 6. 成功标准（Success Criteria）

- SC1：主线任意提交可构建、测试通过；`ctest` 全绿。
- SC2：Simulator / Replay / Serial 三模式共享核心代码（核心层源码只存在一份）。
- SC3：每个任务 100% 有档案，PROJECT_STATUS 与 BACKLOG 始终与事实一致。
- SC4：Simulator Demo 在无外设环境下 30 秒内可演示完整"流量 → 事务 → 统计 → 诊断"链路。
- SC5：一份示例日志可在 Replay 模式复现与 Simulator 一致的诊断结论。
